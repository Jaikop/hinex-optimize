# HinexOptimize — план проекта

Мод-оптимизация для Minecraft Java 26.2–26.4 в духе Lithium / FerriteCore / ModernFix:
ускоряем игру, **не меняя её поведения**.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Загрузчики | Fabric + NeoForge |
| Версии | 26.2, 26.3, 26.4 (снапшоты → релиз), один код через Stonecutter |
| Ниша | Сборник мелких фиксов + оптимизации Vulkan-бэкенда Mojang (`com.mojang.renderpearl`) |
| Поведение | По умолчанию — бит-в-бит как ванилла. Рискованные твики — только опционально, выключены |
| Конфиг | `config/hinexoptimize.properties`, ключ на каждую оптимизацию, Mixin-плагин не применяет выключенные; простой экран настроек без зависимостей |
| Доказательства | Встроенный бенчмарк `/hinexbench` + счётчики + CSV |
| Совместимость | Проверок чужих модов нет; любую оптимизацию можно выключить в конфиге |
| Лицензия | LGPL-3.0 |
| Инструменты | JDK 25 (Temurin 25.0.4), Git 2.55, Gradle 9.6, Loom 1.17, ModDevGradle |

## Что нашли в коде игры (26.3 и 26.4-snapshot-4)

Рендер в 26.x вынесен в библиотеку `com.mojang.renderpearl` (бэкенды `opengl` и `vulkan`).

1. **Нет кэша SPIR-V.** `GlslCompiler.compileToSpv` при каждом запуске и каждом F3+T
   заново компилирует ~114 пайплайнов (~228 шейдеров) через shaderc на CPU.
   С 26.3 это касается и OpenGL.
2. **Нет `VkPipelineCache`.** `VulkanRenderPipeline.compile` вызывает
   `vkCreateGraphicsPipelines(device, 0L, …)`. Пайплайны вне предзагрузки
   (`PipelineCache.get`) компилируются синхронно в главном потоке → фризы.
3. **Лишняя работа на каждый draw call.**
   - `FrontendRenderPass.setPipeline` всегда валидирует и перепривязывает все uniform'ы, даже для того же пайплайна;
   - `VulkanRenderPass.setUniform` всегда помечает дескрипторы «грязными», даже если значение то же;
   - в 26.4 каждый «грязный» draw = новый descriptor set + `vkUpdateDescriptorSets` (в 26.3 — push descriptors);
   - для texel buffer на каждый draw создаётся и удаляется `VkBufferView`.
4. **VMA без флагов** — нет учёта бюджета VRAM (`EXT_memory_budget`) и приоритетов памяти.
5. **Опционально:** shaderc с `optimization_level=0` + debug info; диагностические чекпоинты NV/AMD включены всегда.

Что Mojang уже делает сама (не конкурируем): вывод через DXGI на Windows в 26.4
(`D3D12GpuSurface`), MultiDrawIndirect для террейна.

Код рендера меняется между версиями (например, `GlslCompiler` переехал из
`renderpearl.frontend.shaders` в `blaze3d.pipeline` в 26.4) — поэтому Stonecutter.

## Объяснение простыми словами

- **Кэш шейдеров (SPIR-V).** Игра при каждом запуске «переводит» свои шейдеры на язык видеокарты.
  Мы сохраняем перевод на диск и в следующий раз берём готовый → быстрее запуск и F3+T.
- **Кэш пайплайнов (VkPipelineCache).** То же самое, но на уровне драйвера: видеокарта
  запоминает уже собранные «рецепты» отрисовки → меньше подвисаний при первом появлении эффектов.
- **Меньше лишней работы на кадр.** Игра много раз за кадр повторяет одни и те же
  команды видеокарте. Мы пропускаем повторы → меньше нагрузка на процессор, выше FPS в сценах с мобами.
- **Фоновая компиляция.** То, что игра собирает «по требованию» (и из-за этого дёргается),
  собираем заранее во время загрузки. Экспериментально.

## Архитектура

```
HinexOptimize/
├─ stonecutter.gradle.kts / settings.gradle.kts   # узлы: 26.2|26.3|26.4 × fabric|neoforge
├─ src/main/java/.../hinexoptimize/
│  ├─ core/        конфиг, Mixin-плагин (вкл/выкл по ключам), логирование, абстракции версий
│  ├─ shader/      кэш SPIR-V (+ опц. оптимизация shaderc)
│  ├─ vulkan/
│  │  ├─ pipelinecache/   VkPipelineCache на диске (с проверкой vendor/device/UUID)
│  │  ├─ state/           дедуп setPipeline/setUniform, кэш VkBufferView, переиспользование descriptor set
│  │  ├─ memory/          (опц.) EXT_memory_budget / memory_priority
│  │  └─ diagnostics/     (опц.) выключение чекпоинтов NV/AMD
│  ├─ pipeline/    (эксп.) фоновая прекомпиляция ленивых пайплайнов
│  └─ bench/       /hinexbench, счётчики draw/descriptor/компиляций, CSV, сравнение кадров
└─ docs/
```

### Ключевые детали

- **Ключ кэша SPIR-V** = SHA-256 от: имени и исходника шейдера, типа, define'ов и флагов,
  содержимого всех подключённых include'ов, «device-макросов» (`RENDERPEARL_*`),
  версии shaderc, версии игры и мода. Любое изменение (ресурспак, мод) → промах кэша → обычная компиляция.
- **VkPipelineCache** создаём при создании устройства, подменяем `0L` в вызове
  `vkCreateGraphicsPipelines`, сохраняем атомарно (tmp → rename) после загрузки ресурсов и при выходе.
  Битый или чужой файл просто игнорируется.
- **Дедуп состояния**: пропуск только при точном совпадении (тот же объект пайплайна, `equals` значения uniform'а),
  кэш `VkBufferView` и descriptor set'ов живёт до сброса пула текущего submit'а.
- **Проверка «как ванилла»**: бенчмарк рендерит фиксированную сцену с модом и без
  и сравнивает кадры попиксельно.

## Плавная и динамическая дальность прорисовки (идея пользователя)

### Почему сейчас при смене дальности всё перестраивается

Код одинаковый в 26.2, 26.3 и 26.4:

1. Каждый кадр `LevelExtractor.extract` сравнивает `options.getEffectiveRenderDistance()` с `lastViewDistance`.
2. При отличии вызывается `allChanged()`: новый `SectionUpdateTracker`, где **все секции помечены «грязными»**,
   и флаг `shouldInvalidateCompiledGeometry`.
3. `LevelRenderer.invalidateCompiledGeometry` вызывает `viewArea.releaseAllBuffers()` (выбрасывает все готовые
   меши) и создаёт новую `ViewArea` — дальше вся видимая геометрия мешируется заново.

При этом лишнее только пункт 3: данные чанков клиент сохраняет (`ClientChunkCache.updateViewRadius` копирует их
в новое хранилище), сервер досылает/забывает чанки постепенно.

### Как сделать плавно (`mixin.render.smoothview`, включено)

- Готовый меш секции хранится в `RenderSection.sectionMesh`, а данные на GPU (uber-буферы) привязаны к самому мешу,
  а не к ячейке сетки. Значит меш можно **переложить** в новую сетку для той же позиции в мире — без перестройки и
  без копирования на GPU. Индекс секции нужен только графу видимости, который игра и так сбрасывает.
- Только для смены дальности (другие причины `allChanged()` — ресурспаки, AO, листва — остаются ванильными):
  1. новая `ViewArea` нужного радиуса → граф видимости сброшен на неё → камера выставлена;
  2. для секций, попадающих в обе сетки, меш и время появления переносятся из старой секции в новую;
  3. флаги «грязная» переносятся из старого `SectionUpdateTracker`, так что собранные секции не перестраиваются;
     если у старой секции была незаконченная задача компиляции — секция остаётся «грязной» (не будет устаревшей геометрии);
  4. старая сетка освобождается как в ванилле (оставшиеся меши и задачи).
- Итог: при увеличении дальности добавляются только новые кольца чанков (с ванильным плавным появлением),
  при уменьшении — лишние просто убираются.

### Динамическая дальность (`mixin.render.dynamicview`, по умолчанию выключено)

- Ограничиваем только **эффективную** дальность клиента (`getEffectiveRenderDistance`): настройка в options.txt и то,
  что запрашивается у сервера, не меняются — чанки остаются загруженными, поэтому вернуть дальность дёшево.
- Регулятор: целевой FPS (по умолчанию лимит FPS или 60), окно 2 с по p90 времени кадра; при просадке −1 чанк,
  при запасе и стабильности 5 с +1 чанк; пауза после каждого шага, пока новые секции не собраны; диапазон от
  «установленная − N» (не ниже 4) до установленной.
- Имеет смысл только вместе с плавной сменой: без неё каждый шаг — полная перестройка и новый фриз.

### Как проверим

Новый сценарий бенчмарка `rdswitch`: 12 → 16 → 8 → 12 чанков; меряем максимальный кадр, число перестроенных секций
и время до полной отрисовки — ванилла против мода.

### Итоги

- `render/SmoothViewDistance` + миксины в `mixin/render/smoothview`: перенос мешей, флагов «грязная» и состояния
  плавного появления; учёт незаконченной перестройки секции (`RenderSectionMixin`: запрос новее применённого меша,
  незавершённая задача или запрос моложе 0,5 с — такая секция перестраивается заново).
- **Мир больше не пропадает при переключении.** Ванилла и первая версия мода сбрасывали граф видимости, и пока
  новый граф считался в фоне, список видимых секций был пуст. Теперь список видимых секций перекладывается на новую
  сетку, а отсечение по пирамиде видимости откладывается до готовности нового графа (не дольше 2 с).
  В `rdswitch` считается «пустой кадр» (не видно ни одной секции): ванилла — 160 за три переключения, мод — 0.
- Само переключение после прогрева JIT — 9–15 мс за один кадр (создание сетки и расстановка секций — как в ванилле,
  перенос мешей 2–3 мс, освобождение старой сетки пропускает секции без мешей и задач).
- NeoForge добавляет перегрузки `compileAsync/compileSync/createCompileTask` со списком дополнительных рендереров;
  миксины цепляются к обеим версиям (счётчик — только к той, что реально вызывается).
- Найдена мелочь в ванилле: итератор `RotatingSectionStorage` пропускает последний элемент, поэтому мод обходит
  сетку через `forEach`.
- `render/DynamicViewDistance` + `ViewDistanceController` (чистая логика, 8 юнит-тестов на всех 5 целях);
  числовые настройки `dynamicview.target_fps / min_distance / max_reduction` в конфиге.
- Результаты — в [BENCHMARKS.md](BENCHMARKS.md).

### Что можно улучшить дальше

- Переиспользовать объекты секций вместо создания новой сетки (уберёт оставшиеся 9–15 мс на переключение).
- Плавно двигать туман при смене дальности (сейчас граница тумана прыгает на чанк, как в ванилле).
- Показывать текущую динамическую дальность на экране F3.

## Экспериментальный трек («новые возможности»)

Пробуем после v0.1, каждую идею — сначала замер:

- `VK_EXT_graphics_pipeline_library` — почти мгновенная сборка пайплайнов из готовых частей.
- Оверлей GPU-времени по проходам рендера (у игры уже есть `GpuQueryPool` и `TracyGpuProfiler`).
- Показ использования VRAM через memory budget.
- Асинхронная загрузка текстур через отдельную transfer-очередь.
- Мелкие фиксы в духе ModernFix — по результатам профилирования (запуск, утечки памяти, редкие лаги).
